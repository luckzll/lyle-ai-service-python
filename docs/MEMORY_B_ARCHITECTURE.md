# B 方案：统一事实、分层使用（2026-09-08）

## 数据职责

唯一的当前事实入口是 `app/memory/fact_store.py`。每条确认事实有独立 factId、schemaPath、value、status、revision、confidence、expiresAt 与来源标识。多值槽位按明确列表分隔符拆分为事实，不用“和/与”等自然语言字符拆分。相同用户、槽位、规范化值的重复确认复用事实 ID；独立来源仍保留在证据层。语义相似但不相同的事实不自动删除。

- PostgreSQL `memory_fact`：每条事实独立记录，包含当前状态及修订信息；被替换的事实保留为 superseded 历史。
- `memory_fact_owner`：每用户的迁移状态、迁移报告和单条治理审计元数据；行锁序列化事实写入。事实变更与 Schema 队列失效标记在同一 PostgreSQL 事务提交。
- `user_profile`：保留 ID、来源外键与使用统计；旧值只作迁移输入，不再作为新模式的当前值。新建锚点的 value/summary 为空。
- `profile_store.py` 的现有接口作为兼容门面：读取返回事实汇总，确认/纠正/状态命令转发事实库；摘要更新不能反向改变事实。
- `structured_memory`：继续承载 pending 候选；原已确认记录保留为迁移归档，新模式不再双写。兼容查询中的已确认数据从事实投影返回。
- fragment / evidence：继续保存原文及来源。模型构建只接收当前确认事实值和来源引用，不把可能包含已停用兄弟事实的整段原文重新提供给构建模型。
- Schema：只读、版本化派生快照，携带 factIds/factRevisions。不是另一套可以独立修改的当前资料。

代码固定槽位定义仍为 35 项（33 项普通字段、2 项治理字段），不是 Agent 自由创造任意字段。

## 每轮提供给模型的内容

1. **精简核心画像**：当前确认事实的直接只读投影，不等待 Schema 构建。优先顺序为边界、触发点、沟通风格、输出风格、语言、语言习惯、称呼、职业；默认最大 1200 字符，仍受总上下文预算限制。过长条目整条跳过；敏感、治理、失效和低置信度事实不注入。
2. **当前会话上下文**：最近消息；full 分支还可使用当前会话摘要。核心画像不是全部聊天历史，也不是全部个人偏好。
3. **当前项目/任务背景**：复用项目系统的当前阶段、活跃目标、决策和下一步建议，不另外复制进事实库。显式指定项目或唯一的会话关联可以延续；多个关联项目不猜测，相关追问要求澄清；不自动沿用已结束/归档项目。新会话没有关联时不会凭空延续某个任务。
4. **详细个人记忆**：先按问题选择场景/路径，再读取该子集；小 Schema 也先过滤。小子集直接选取，大子集由只读 Agent 多轮读取；单次筛选、模型异常规则降级仍保留。模型规划失败后为规则选择，不保证覆盖所有自然语言表达。

核心层与详细层按同一槽位的事实投影去重，最终 usedMemories 只从预算内条目生成；新增 CORE_PROFILE 原因码。当前工作汇总工具不再清空新模式的核心记忆。所有非空正常聊天（包括问候）走至少 light，空输入仍跳过。

“安排一周学习计划”无需含“职业”二字：职业可来自核心画像，学习目标由计划场景召回；短期消息消失不影响已确认事实保存。但未确认信息、未关联任务、过期目标不能保证自动找回。

详细召回的项目类个人槽位与项目系统不是同一类数据：个人槽位是用户级资料；项目系统负责真实项目权限、状态与会话关联。不能将用户级历史偏好当作项目当前状态或自动完成任务。

## 增量构建与失效

后台按槽位的输入指纹比较，只给模型重新构建变化槽位，其余复用上个成功版本。事实 ID、修订或来源改变都使对应槽位失效；不存在跨槽位推理的构建依赖。校验后仍原子发布一份完整快照。手动 /schema/rebuild 强制全量构建，用于修复、模板升级；修改槽位定义/构建规则后应主动全量重建。

核心事实修改立即反映在下一次读取；详细旧槽位因指纹不符被过滤，等待新快照。Agent 多轮执行结束再校验一次。并发事实修订采用 expectedRevision；过时请求返回 409，跨用户事实 ID 返回 404。

停用/过期/被替换事实参与旧摘要的文本治理过滤；该过滤不是完美的语义撤销。当前对话原文仍是用户会话记录，不宣称被永久删除。

## API 与页面

Java 绑定当前登录用户，Python 内部接口仍要求 internal token：

- GET `/memory/facts` → 事实列表、迁移报告；Python `/ai/memory/{user_id}/facts`。
- PUT `/memory/facts/{factId}` → `{expectedRevision, status?, value?}`；修改某一事实，不替换同槽位其他事实。重复值冲突/过时版本返回 409。
- 原 profile:<id> 纠正、停用、来源、冲突治理接口仍可用，语义是对整组槽位操作。
- 原 `/memory/schema`、`/schema/rebuild`、`/schema/recall` 保留；状态包含 factsEnabled。

Vue 在现有记忆页高级模式显示独立事实，可单独停用/恢复。新模式的构建提示区分“核心画像可用”和“详细记忆等待整理”。迁移冲突提示用户核对，不自动选择新旧值。

## 安全迁移与运行

1. 先备份并在隔离环境升级 Alembic 至 `0030_memory_facts`（包含前置 0029）。此为 Python PostgreSQL 表，不修改 Java MySQL 业务表。
2. 默认 `MEMORY_SCHEMA_ENABLED=true`、`MEMORY_FACTS_ENABLED=true`。首次访问某用户的新记忆接口/召回时，在用户行锁下执行一次幂等迁入，保留旧画像 ID。旧画像与旧结构化行的不同 active 值保守标记 conflicted；报告列出需要核对的字段。已有治理状态不自动恢复。
3. 校验迁移报告、事实和来源数、典型召回、治理与单条操作后再推广。旧表目前保留，不进行物理删表，不做后台双向同步。
4. 发生问题优先修复新事实或重新构建快照。**迁入后不能简单关闭开关当作安全回滚**：旧记录已停止同步，切回旧模式会读取旧数据。完整回退需要基于新事实做受控反向迁移；本次未实现自动反向迁移或旧表清理。
5. `POSTGRES_ENABLED=false` 仅适用于测试/单进程开发；进程内事实及队列不跨重启/多进程共享。

永久删除仍走现有异步治理任务，清理事实当前值/历史、归档结构化行、画像锚点、来源和 Schema 历史。迁移完成标记保留，防止同用户后续读取重新导入归档数据。单条停用不是物理删除。
